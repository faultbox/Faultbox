# v0.17.0 — RFC-052 Agent-First Surface (first slice)

Plan for [RFC-052](../rfcs/0052-agent-first-surface.md) Gaps 1, 2 and 8, plus the
deprecation removals promised for v0.14.0.

Scope decision (2026-07-30): **foundation + vacuity.** Gaps 3–7 are deferred; everything
in the RFC reports through this slice, so it goes first.

## The theme

**An agent finds out that its spec cannot fail — and, where possible, before running it.**

"Where possible" is doing real work in that sentence. M0 established that the most valuable
of the three diagnostics needs run-time data and therefore cannot live in `faultbox check`.
The theme survives, but not in the tidy form the scope decision assumed.

## M0 — measure first ✅ done, and it falsified the premise

Ran before writing any checker, to make the RFC's claim a number rather than an assertion.
It came back smaller than expected and pointed at a different failure mode — which is the
whole reason to measure first.

**Measured at `release-0.16.0`** (before `poc/protocol-audit/` existed), across
`poc/**/*.star` + `recipes/*.star`:

| Metric | Result |
|---|---|
| Tests total | 58 |
| Tests evaluating zero assertions | **11 (18%)** — all in `poc/gvisor-rfc054/faultbox.star` |
| Step calls discarding their result | 8 matches, of which **1 true positive** (`bus.main.publish` in `poc/mock-demo`) |
| False-positive rate of the naive AST pattern | **2 of 3** DB-ish hits — `e.fields.get("event")` matches `ident.ident.ident(...)` |
| `poc/` specs calling a SQL step at all | **1** (`poc/gvisor-rfc056`, added in v0.16.0) |

### What the measurement changed

The original Gap 8 sketch assumed the dominant problem was tests that assert nothing, with
discarded step results second. Neither is dominant:

**`poc/` barely exercised SQL steps at all** — one spec, added in the release that found the
first bug. So the initial diagnosis ("specs discarded their results") was wrong; the
coverage simply was not there.

**But CI did exercise it.** `testops/corpus/postgres_fault_basic.star` has called
`pg.main.query()` against a real `postgres:16-alpine` on every PR since before v0.15.0 —
and passed throughout, because:

1. it sets `POSTGRES_HOST_AUTH_METHOD: trust`, removing the credential path from the test;
2. it asserts the query **fails** (`not resp.ok`) under an injected fault — which a
   completely broken client satisfies identically.

Its own comment states the intent: *"so this test doesn't depend on authentication
round-tripping."* A careful test, and the care is what hid the bug.

**Conclusion: mode 3 (no positive control) is the target**, not mode 1 or 2. RFC-052's
Gap 8 was rewritten accordingly, and `NO_POSITIVE_CONTROL` is now the lead diagnostic.

### Consequence for sequencing

`NO_POSITIVE_CONTROL` is suite-level and needs run-time data, so it **cannot** ship inside
`faultbox check`. That cuts against this release's theme ("find out what is wrong without
running anything") and is accepted rather than papered over — see RFC-052 open question 7.
The two cheap diagnostics run in `check`; the valuable one runs after a suite.

## M1 — `NO_POSITIVE_CONTROL`

The lead diagnostic. Suite-level, computed after all tests in a run complete.

**Definition.** For each service interface on which at least one step was executed during
the run: if no test asserted that a step on that interface **succeeded**, emit the
diagnostic.

**Determining "asserted success" without judging assertion strength.** Do not parse
assertion expressions. Instead use what the event log already records: a step that returned
`Success: true` inside a test that **passed** and that executed at least one assertion,
with **no fault active on that interface**, is a positive control. That is structural and
needs no semantic judgement.

Rationale for "no fault active": a step succeeding *while* a fault is injected proves the
fault did not fire, not that the client works.

**Gate.** Must fire on `testops/corpus/postgres_fault_basic.star` as it stood at v0.15.0,
and must **not** fire on any `poc/protocol-audit/*.star` spec. Those are the known-bad and
known-good cases respectively; a version that fails either is wrong.

### M1 results ✅

Both halves of the gate pass, and the diagnostic found a real bug on its first run.

| Check | Result |
|---|---|
| Fires on the known-bad shape (`poc/protocol-audit/_gate-no-positive-control.star`) | ✅ fires, on a **green** suite |
| Silent on all eight `poc/protocol-audit/*.star` | ✅ 0 fires |
| Wider `poc/` suite (6 more specs) | 1 fire, **1 true positive, 0 false positives** |
| Unit coverage | 15 tests over the state machine and the wrapper wiring |

**The true positive.** `poc/mock-demo/faultbox.star:119`:

```python
def test_kafka_broker_responds():
    """Real kafka publish reaches the kfake-backed broker."""
    bus.main.publish(topic = "orders", key = "o-1", value = '{"id":1}')
    # publish() returns success when the broker accepts; assertion is the
    # absence of a panic.
```

The rationalising comment is the tell: a publish that never reaches the broker
returns `ok=False`, it does not panic. The test asserted its own docstring and
nothing else, and would have passed against a completely dead broker. Fixed in
the same change. It is also the one instance M0's `STEP_RESULT_DISCARDED` scan
found — the two diagnostics agree, from different directions.

**Two design deviations from this plan, both deliberate:**

1. **Dropped the "no fault active" condition** on what counts as a positive
   control. The plan called for it; it was wrong. If a step *succeeded*, the
   client demonstrably worked whether or not a fault was installed — a fault that
   was installed and did not fire is a different problem that `FAULT_NOT_FIRED`
   already reports. Requiring fault-free success would only make the diagnostic
   miss real positive controls.
2. **The assertion counter shipped with M1, not M2.** M1's gate needs "the test
   asserted at least once" to stop a vacuous test silently supplying the control
   the suite lacks, so the counter is a prerequisite rather than a successor.

**One thing the gate caught in my own work:** `TestAssertionBuiltinsAllExist`
failed on its first run because I had listed `test_panics`, `test_b_panics` and
`test_panic_body` in `assertionBuiltins` — they are Go test fixtures in the
`star` package, not spec builtins. A grep for `NewBuiltin(...)` had picked them
up out of `_test.go` files. That is precisely the rename/typo case the gate
exists for, and it fired on day one.

## M2 — `TEST_NO_ASSERTIONS` and `STEP_RESULT_DISCARDED`

The two cheap ones, which do run inside `check`.

### `TEST_NO_ASSERTIONS`

Per-test counter incremented wherever an assertion is evaluated. Must count:

- `assert_true` / `assert_eq` / `assert_never` / `assert_eventually` / `assert_before`
- `expect_success` / `expect_error_within` / `expect_hang` / `test_panics` family
- **`test(..., expect=...)` expectation evaluation** — open question 6. A declarative
  `expect=` asserts with no `assert_*` in the body; counting only body calls fires this on
  correct specs, the one outcome that would discredit it.
- `eventually()` / `always()` property finalisation, `monitor()` `check=` evaluation

**Gate:** runs clean against every existing spec that does assert. Expected to fire on the
11 known tests in `poc/gvisor-rfc054/faultbox.star` and nowhere else in `poc/`.

### `STEP_RESULT_DISCARDED` — **CUT**, by the pre-committed rule

**Recorded decision: cut from v0.17.0.** The rule above was written before
measuring precisely so this could not be rationalised afterwards, and the
measurement says cut.

Implemented with receiver resolution as specified — resolving `db.main.exec(...)`
against the loaded topology rather than matching on shape. That worked: the
shape-based false positives M0 found (`e.fields.get("event")`) disappeared
entirely. Then it was measured across `poc/` + `recipes/` + `testops/corpus/`:

| | Count |
|---|---|
| Specs scanned | 54 |
| Findings | 15 |
| **Legitimate discards (false positives)** | **13** |
| True positives | 2 |

The false positives are not near-misses; they are a distinct and correct idiom —
**the step is used for its side effect, and its result is genuinely irrelevant.**

```python
# testops/corpus/determinism_clock_read.star
def scenario():
    # GET /trigger?leak=clock — leaker performs a raw
    # clock_gettime syscall before responding.
    leaker.main.get(path = "/trigger?leak=clock")
```

The step is a *trigger*. The assertion is on the emitted `unmediated_io` events,
not on the HTTP response. Eight findings are this pattern. Five more are
`poc/raft-cluster` posting to a node it has just **partitioned**, where failure
is the expected outcome and the assertion is about cluster recovery afterwards.

Distinguishing "I want the side effect" from "I forgot to check" is an intent
question, not a syntactic one. A heuristic tuned to exempt these — say, steps
inside a `fault()` scenario — would be post-hoc curve-fitting to 15 data points,
and would make the diagnostic's behaviour unpredictable. Unpredictable
diagnostics get muted, and a muted diagnostic is worse than an absent one.

**Cutting costs almost nothing**, which is what makes the decision easy. Both
true positives are already caught by the other two diagnostics:

- `poc/mock-demo` — caught by `NO_POSITIVE_CONTROL` in M1, already fixed.
- `testops/corpus/kafka_basic.star` — both its tests assert *nothing at all*, so
  `TEST_NO_ASSERTIONS` catches them. Fixed here.

Both carried the same false belief in a comment: *"the assertion is the absence
of a panic"*. A step that fails returns `ok=False`; it does not raise. That
misconception is the actual bug, and the two shipping diagnostics find it.

The implementation is deleted rather than left dormant behind a flag — dead code
is worse than no code, and this document holds the analysis a future attempt
would need.

### M2 results ✅

| Check | Result |
|---|---|
| `TEST_NO_ASSERTIONS` false positives across 11 runnable specs | **0** |
| `NO_POSITIVE_CONTROL` false positives across the same 11 | **0** |
| `TEST_NO_ASSERTIONS` fires on a vacuous passing test | ✅ |
| True positives found in the repo | 2 (`mock-demo`, `kafka_basic`) — both fixed |
| `STEP_RESULT_DISCARDED` | cut, 13/15 false positives |

**Two design decisions worth recording:**

1. **Assertion counting moved to `registerExpectation()`.** It is the single
   point where all three registration paths converge — `eventually()`,
   `always()`, and `test(expect=...)`. Counting in the builtin wrapper instead
   would have missed `test(expect=)` entirely, since that never passes through a
   builtin, and a correct declarative test would have been reported as vacuous.
   That was open question 6, and this closes it.
2. **`TEST_NO_ASSERTIONS` fires only on tests that passed.** A failed, errored,
   timed-out or halted test may have stopped before reaching its assertions, and
   "you asserted nothing" stacked on top of a failure is noise attached to a
   message the user is already reading.

**Found along the way:** per-test diagnostics have existed since v0.12 but were
only ever written to JSON and the bundle — never printed. So
`FAULT_FIRED_BUT_SUCCESS` and its five siblings have been invisible to anyone
running `faultbox test` interactively since they were added. Warnings now print
after the summary. `TestResult.Assertions` is also exposed in JSON, because an
agent reading a green result needs to know whether anything was checked.

## M3 — error-code taxonomy## M3 — error-code taxonomy

Extend the existing `Diagnostic{Level, Code, Message, Suggestion, Service, Syscall}` to
load-time and infrastructure failures. Starting set, to be confirmed against actual error
paths rather than invented:

| Code | Source |
|---|---|
| `SPEC_SYNTAX` | Starlark parse failure |
| `SPEC_UNKNOWN_SERVICE` | reference to an undeclared service |
| `SPEC_UNKNOWN_KWARG` | the strict-kwarg validation added in v0.13.2 |
| `SPEC_FORBIDDEN_LAMBDA` | monitor/assume AST denylist |
| `SPEC_UNSUPPORTED_ON_REMOTE` | syscall fault on `service(remote=)` |
| `HEALTHCHECK_TIMEOUT` | `waitReady` exhaustion |
| `LAUNCH_EXEC_NOT_FOUND` | binary mode, missing executable |
| `IMAGE_PULL_FAILED` | container mode |
| `DOCKER_UNAVAILABLE` | no daemon |
| `TRACE_HOST_NOT_REGISTERED` | `watch()` without `setup-trace` |

**Gate: every code carries a `suggestion`.** A code without one is a code the agent must
guess about, which defeats the purpose. Enforce with a table-driven test asserting
non-empty `Suggestion` for every registered code — the enforcement is the test, not
reviewer diligence.

## M4 — `faultbox check`

```
faultbox check <spec.star> [--format text|json] [--strict-vacuity]
```

Runs `LoadFile` plus plan enumeration. **Launches nothing** — no Docker, no processes, no
network. That property is the whole value and needs a test that would fail if a future
change introduced a launch.

Exit codes, following the existing convention (`test` uses 2 for fail, 3 for
inconclusive-only):

| Code | Meaning |
|---|---|
| 0 | no findings, or warnings only |
| 1 | usage error |
| 2 | one or more `error`-level findings |

Warnings do not fail the command; an agent branches on the JSON, and CI can opt in with a
flag rather than having the default forced on it.

MCP tool `check_spec` returns the same structure. Note the manifest currently records
`faultbox mcp` as having **no test coverage at all** (🔴) — adding a tool without fixing
that makes the row worse, so M4 includes contract tests for the new tool at minimum.

## M5 — deprecation removals

| Removal | Replacement | Warned since |
|---|---|---|
| `faultbox generate` | `faultbox plan --suggest` | v0.13.0 |
| `stdout()` / `stderr()` | `observe.stdout` / `observe.stderr` | v0.13.0 (RFC-044) |
| `json_decoder()` / `logfmt_decoder()` / `regex_decoder()` | `decoder("json"\|"logfmt"\|"regex")` | v0.13.0 (RFC-044) |

Each removal must produce a **legible failure**, not a bare "unknown identifier" — a spec
written against the old API should get an error naming the replacement. That is the same
principle as M3: the error is the agent's next move.

Sweep `poc/`, `recipes/`, `docs/` and `testops/` for uses before removing, and check the
tutorial — a removed builtin still shown in a tutorial chapter is a worse bug than the
deprecation.

## Risks

**`NO_POSITIVE_CONTROL` is a heuristic about test adequacy.** The dominant risk, and a new
kind for this codebase: every existing diagnostic reports something that *happened*, while
this one reports something that *did not*. Absence is easier to get wrong. The M1 gate —
must fire on the known-bad spec, must stay silent on the eight known-good ones — is the
guard, and it is a weaker guard than the ones protecting the other diagnostics. If it
cannot satisfy both halves of that gate, it should not ship.

**The diagnostics cry wolf.** A warning that fires on correct specs gets muted, and a muted
diagnostic is worse than absent — it converts signal into noise the agent learns to ignore.
Mitigated by M0 measuring first, M2's pre-committed cut rule, and gates on existing
passing specs throughout.

**`STEP_RESULT_DISCARDED` is barely worth having.** M0 found one true positive in the whole
repository and a 2-in-3 false-positive rate from the naive detector. It is syntactic: it
cannot see `r = db.main.exec(...)` followed by never reading `r`. Kept only because it is
cheap and runs in `check`; the pre-committed rule cuts it at the first false positive.

**None of the three proves test adequacy.** They detect three specific structural
mistakes. The docs must not imply more — a suite that passes all three checks can still be
worthless, and claiming otherwise would recreate the false confidence this whole RFC exists
to attack.

**Scope creep into Gaps 3–7.** `check_spec` sits next to the bundle ops of Gap 3, and it
will be tempting to add "just `bundle_summary`". Deferred means deferred; the release is
coherent without it.

**The deprecation removals break someone.** Pre-announced twice, and the warnings have
shipped since v0.13.0 — but they named v0.14.0 as the removal version, so anyone reading
carefully concluded the removal already happened and their code was fine. Call this out
explicitly in the release notes rather than treating "we warned you" as sufficient.
