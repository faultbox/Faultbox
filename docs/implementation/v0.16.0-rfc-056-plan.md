# RFC-056 implementation plan — filesystem observation

**Target:** v0.16.0
**Branch:** `epic/v0.16.0-watch`
**RFC:** [RFC-056](../rfcs/0056-filesystem-observation.md) · **Issue:** [#148](https://github.com/faultbox/Faultbox/issues/148)

---

## Milestone 0 — overhead: resolved

The RFC named one unmeasured item, and it gated the design: *what does a
traced-but-unwatched container pay?* If it were expensive, tracing would have to
be opt-in per service, which changes both the DSL surface and the install story.

Measured 2026-07-29 in Lima (kernel 6.8, runsc `release-20260721.0`, alpine),
five runs per case, workload = 20,000 × 4 KiB writes plus 1,000 file creates:

| Case | Avg wall time |
|---|---|
| plain `runsc` — baseline | 316 ms |
| `runsc-trace`, sink **absent** | 284 ms |
| `runsc-trace`, sink **present** | 373 ms |

**Registering the runtime is free when idle.** The absent-sink case is
indistinguishable from baseline — faster, in fact, which is simply noise at this
sample size. A user who registers `faultbox-trace` and never runs Faultbox pays
nothing, which is what makes a one-time host registration acceptable.

**Tracing costs ~18% on a workload doing 280,000 trace points per second.** That
is a pathological rate, reached here only by `dd`-ing 80 MB through 4 KiB
writes. It is a ceiling, not a typical cost.

### Decision

**Register the runtime broadly; do not make tracing opt-in per service.** The
idle cost is zero and the active cost is bounded and only reached by workloads
that are themselves unusual. Per-service opt-in would buy little and complicate
both the DSL and the install path.

## Milestone 0b — drops: a finding the RFC must absorb

The same runs surfaced something the RFC did not anticipate. A volume sweep:

| Trace points | Elapsed | Rate | **Dropped** |
|---|---|---|---|
| 1,003 | 279 ms | 3.6 k/s | **0** |
| 4,910 | 285 ms | 17 k/s | **0** |
| 19,927 | 423 ms | 47 k/s | **76** |
| 49,958 | 688 ms | 73 k/s | **45** |
| 104,212 | 373 ms | 280 k/s | **94** |

**The sink starts losing points somewhere between 17 k/s and 47 k/s.**

`seccheck.Sink.Dropped()` already exists and its v0.14.0 comment says why:

> Non-zero means the sink could not keep up and the observation is incomplete —
> which must be surfaced, not averaged away.

That comment is now load-bearing. The canonical `watch()` use is an audit:

```python
assert_never(lambda e: e.type == "file_io" and
             not e.data["path"].startswith("/var/lib/app"))
```

A dropped point could be the violating one. An audit that missed 76 operations
cannot honestly claim "never" — it can only claim "never, among the ones I
saw", which is not the assertion the spec author wrote.

**So drops must fail the test**, in the same way and for the same reason as
packet rules installed against an absent gateway. This is not a rate to tune
away; it is a correctness boundary that has to be visible.

Secondary: the drop count does *not* rise monotonically with volume (76 at
20 k, 45 at 50 k). That points at burstiness rather than sustained throughput —
worth understanding before assuming a bigger buffer fixes it.

## Milestone 0c — the default point set is too wide

The drop numbers above were measured with **three** trace points. RFC-054's
`FileIOPoints()` requests **eight**, including `read`, `pread64`, `close` and
`connect`. Re-measured on a read-heavy workload (write 20 MB, read it back
four times):

| Points requested | Delivered | **Dropped** |
|---|---|---|
| 3 — `openat`, `write`, `pwrite64` | 25,015 | **0** |
| 8 — the RFC-054 default | 48,576 | **1,488** |

Reads roughly double the volume and take the drop count from zero to fifteen
hundred, on a workload that is not extreme. Combined with M0b's rule — drops
fail the test — **the inherited default would make `watch()` fail on ordinary
read-heavy services.**

### Decision

Ship the narrow set: `openat`, `write`, `pwrite64`, `writev`. Make `read`,
`pread64`, `close` and `connect` opt-in at `setup-trace` time.

This adds a requirement to M3: the DSL already accepts `ops=["read"]`
(`watchableOps`), so with a narrow host config that watch would observe nothing
and pass vacuously — v0.14.0's failure mode, reintroduced through the back
door. It must fail at spec load naming the fix, exactly as `ops=["fsync"]`
already fails naming gVisor's missing trace point.

## Milestones

Each ends with a green `make lint && make test` on macOS and the Linux CI
matrix.

| M | Title | Exit criterion |
|---|---|---|
| **0** | Overhead + drops + point set | ✅ Done — decisions above |
| **1** | Host registration | ✅ Done — `faultbox setup-trace`, idempotent, reports every change, prints the restart rather than performing it. |
| **2** | Sink lifecycle | ✅ Done — binds the host-configured endpoint, releases cleanly, refuses to steal a live sink, reclaims a stale one. |
| **3** | Un-gate `watch()` | ✅ Done — refusal replaced by a deliverability check; sink binds the host endpoint; containers launch under `faultbox-trace`; `FileIOPoints()` narrowed. |
| **4** | Honesty guards | ✅ Done — six guards: never started, no sandbox connected, decode error, drops, unattributed points, plus the attribution fallback M3 silently broke. |
| **5** | Scenarios + docs | ✅ Done — audit corpus in `poc/gvisor-rfc056/`, tutorial ch. 28, spec reference, `fs-unmediated` implemented. |

Milestone 4 is not optional polish. Without it the feature ships the exact
failure mode v0.14.0 withdrew `watch()` to avoid — a green audit that observed
less than it claimed.

## Risks

| Risk | Mitigation |
|---|---|
| Drops make high-I/O services unwatchable | M4 makes it loud rather than silent. Buffer sizing is a follow-on once burstiness is understood. |
| A user's `daemon.json` is hand-managed or generated | M1 is idempotent and never writes implicitly; it reports what it would change. |
| Concurrent runs | Deliberately blunt in v1: second run fails with a clear message. `container_id` routing is a follow-on. |
| gVisor version drift | `--pod-init-config` is undocumented in `runsc --help`. Pin the tested runsc version in docs and check it in `setup-trace`. |

## Open questions

Closed by M0c: `close` and `read` are available but **off by default**, opt-in
via `setup-trace`, on the volume evidence above.

Still unanswered; neither blocks M1:

1. **No `fsync` trace point in gVisor**, so durability auditing stays out of
   reach. Worth an upstream contribution?
2. **Why are drops bursty rather than proportional?** 76 at 20 k points, 45 at
   50 k. Until that is understood, a larger buffer is a guess rather than a fix.

## What the first real end-to-end run cost

Four defects, none of which unit tests could have found, all from running
`watch()` against a live Postgres for the first time:

1. **The healthcheck lied.** `tcp()` probes the port Docker published, and
   Docker's proxy binds it the moment the container starts — before Postgres
   listens. It reported ready in 0 ms against a backend needing ~10 s, so the
   body ran and tore the sink down mid-boot: 18 trace points where a standalone
   sink over the same boot saw 29,426. Faultbox has no exec- or log-based
   readiness gate; a spec-level settle is the honest workaround, and the gap is
   worth closing separately.

2. **The guard failed correct runs.** `stopServices()` closes the sink *before*
   the per-test guard reads its state, so a run that resolved 128 real paths was
   failed with "filesystem observation never started". A guard that fails
   correct runs is worse than no guard — it makes the feature unusable while
   looking like a safety feature. Fixed with a teardown snapshot.

3. **Boot drops would have failed every database.** A bare `postgres:16-alpine`
   boot produces ~29k points and ~1.2k drops before any test body runs. A
   lifetime drop count therefore condemned every `watch()` on a real database
   for I/O the spec never looked at. Drops are now measured within the watch
   window.

4. **Per-test state leaked.** `closeFSObservation` reset the sink and session
   map but left `containers` populated, so each test added its sandbox ID and
   the map grew. At two entries the single-sandbox attribution fallback
   disables itself and every ID mismatch becomes an unattributed point —
   presenting as *the first tests in a suite pass and the later ones fail*.

Worth recording because the pattern repeats: each one produced a result that
looked like a property of the system under test and was a property of the
instrument.
