# v0.18.0 — Field-report fixes (inDrive courier, 2026-08-14)

Six issues from the first onboarding of a large production Go service
(Uber Fx, ~30 gateways, MySQL + Redis + Kafka, sarama + go-redis +
grpc-go). Reported against v0.17.0, reproduced on v0.16.1.

This is a defect release. No new surface, no RFC. The ordering below is
by the reporter's severity, which matches ours: F-1/F-4 make Faultbox
unusable for the class of service it is sold for.

Status of each root cause: **confirmed** means traced to a specific line
and mechanism; **mechanism identified** means the code path is
understood but the failure has not been reproduced end to end here.

---

## F-1 / F-4 — One bug, not two: the notification loop dies silently

Reported as two issues (host-binary SUT loses all outbound sockets;
proxy data plane freezes). They are the same defect. The proxy is
incidental — the SUT's syscalls are dead either way, which is why the
signature is identical on the direct and proxied paths.

**Root cause — confirmed.**

`seccomp.Receive` returns an error when `SECCOMP_IOCTL_NOTIF_RECV`
fails ([`internal/seccomp/filter_linux.go:310`](../../internal/seccomp/filter_linux.go)):

```
ioctl(SECCOMP_IOCTL_NOTIF_RECV): no such file or directory
```

`ENOENT` here means **this notification is gone** — the target thread
died or was interrupted before the supervisor received it. It is a
routine, per-notification transient. It does *not* mean the listener fd
is closed.

`isClosedFdErr` ([`internal/engine/launch_linux.go:638`](../../internal/engine/launch_linux.go))
classifies it as a closed fd anyway, by substring-matching the errno text:

```go
return strings.Contains(errStr, "bad file descriptor") ||
    strings.Contains(errStr, syscall.EBADF.Error()) ||
    strings.Contains(errStr, syscall.ENOENT.Error())   // <-- wrong
```

So in `notificationLoop` ([`launch_linux.go:285`](../../internal/engine/launch_linux.go)):

```go
req, err := seccomp.Receive(listenerFd)
if err != nil {
    if isClosedFdErr(err) {
        return nil          // ENOENT lands here: clean, silent exit
    }
    ...
}
```

the loop returns `nil` and stops forever. The caller suppresses the log
line precisely because the error is `nil`
(`if err != nil && !isClosedFdErr(err)`), so **nothing is printed**. The
child process still carries its seccomp filter, with no supervisor left
to answer it. Every subsequent intercepted syscall blocks indefinitely.

Verified: a `Receive` ENOENT is classified as a closed fd.

```
ENOENT from RECV    -> isClosedFdErr = true   (want false)
EBADF (real close)  -> isClosedFdErr = true   (want true)
```

This accounts for every detail in the report:

| Reported | Explained by |
|---|---|
| every read times out **and** new dials time out | `read` and `connect` are both intercepted; nothing answers either |
| "It never recovers" | the loop is not restarted, and nothing detects it exited |
| MySQL container stays healthy | the container is fine; the SUT's syscalls are not |
| spec's own probes to the same service succeed | faultbox is not filtered |
| high-connection-count pool always dies, small Redis client sometimes survives | ENOENT probability scales with concurrent notification volume |
| "the moment the first test step runs" | that is when traffic — and notification volume — spikes |
| same signature on the proxy path (F-4) | the proxy is irrelevant; the SUT's syscalls are dead |

The Go runtime makes this far more likely than it looks: `SIGURG`
preemption interrupts syscalls constantly, and a large fx graph with a
DB pool has many threads in flight. A quiet single-threaded demo almost
never trips it, which is why the corpus has never caught it.

Both launch paths share the loop, so containerized and host-binary SUTs
are equally affected
([`launch_container_linux.go:66`](../../internal/engine/launch_container_linux.go)).

The `ENOENT` clause dates to `81be9d0` (2026-03-24), the original
unified launch commit. It has been latent since.

**Fix.**

1. Stop substring-matching errnos. Use `errors.Is(err, syscall.EBADF)` /
   `errors.Is(err, syscall.ENOENT)` against wrapped errnos, so
   classification cannot drift with message wording.
2. Split the two meanings. `ENOENT` from `RECV` is **skip this
   notification and continue**. Only `EBADF` / `POLLHUP` / a closed
   listener ends the loop.
3. Make a premature exit loud instead of silent. If the loop ever
   returns while the child is alive, that is a supervisor failure: log
   it at error level, record a `supervisor_exited` event, and fail the
   test with a legible reason. A filtered process with no supervisor
   must never be a silent hang — this is the property that turned a
   transient into a two-day debugging session for the reporter.
4. Count skipped notifications and surface the total in the teardown
   summary, so "we dropped 12 notifications" is visible rather than
   inferred.

**Tests.**

- Unit: table over `(errno, wrapped form) -> classification`, including
  the exact `Receive` wrapping.
- Unit: a fake listener that returns ENOENT once, then a valid
  notification — assert the loop survives and processes the second.
- Integration: a Go SUT with a 25-connection pool doing continuous
  round trips under an installed filter, run for 60 s. Assert zero
  stalled syscalls and that the loop is still alive at teardown. This
  is the regression gate; it is also the corpus gap that let the bug
  ship.

**Risk.** Low. The change narrows an exit condition. The failure mode of
getting it wrong is a loop that runs slightly longer than needed at
teardown, which the existing `stopNotif` / fd-close path already covers.

## F-2 — `mock_service` is unreachable from a containerized SUT

**Root cause — confirmed.** Two independent gaps that must both be fixed:

1. **Bind address.** [`internal/star/mock_runtime.go:67`](../../internal/star/mock_runtime.go)
   hardcodes `addr := fmt.Sprintf("127.0.0.1:%d", iface.Port)`. No
   override exists. Proxies already solved this —
   [`internal/proxy/listen.go`](../../internal/proxy/listen.go) defaults
   to `0.0.0.0` on Linux with a `FAULTBOX_PROXY_BIND` override, added
   with RFC-035 in v0.12.28. Mocks were never brought along.

2. **Env substitution.** The `host.docker.internal` rewrite
   ([`runtime.go:3470`](../../internal/star/runtime.go)) sits behind
   `if proxyAddr == "" { continue }`, and mocks are explicitly excluded
   from `preStartProxies` ([`runtime.go:2187`](../../internal/star/runtime.go)).
   No proxy → no substitution → the SUT gets a raw `localhost:9095`
   that resolves to its own container.

The reporter's read — "an oversight specific to mock services" — is
exactly right.

**Fix.** Reuse the proxy's bind resolution for mock listeners, and make
the container-consumer substitution independent of whether a proxy
exists, keyed on the service having a reachable listener at all.

**Tests.** Spec-level: containerized SUT + `mock_service`, assert the
SUT reaches the mock. This topology has no coverage today, which is why
it shipped broken.

**Risk.** Low-moderate. Binding mocks to `0.0.0.0` exposes them to the
LAN on Linux, the same trade the proxy already makes. Carry the same
override and document it alongside `FAULTBOX_PROXY_BIND`.

## F-3 — Docker embedded DNS black-holes from the second test onward

**Mechanism identified.** The network is created and destroyed **per
test**: [`runtime.go:3181`](../../internal/star/runtime.go) removes it
whenever no container survives the test
(`if len(keptContainers) == 0 && rt.networkID != ""`). An N-test suite
performs N create/destroy cycles on the same-named network. The
reporter attributes the embedded-DNS failure to that churn, which is
consistent with the evidence they give (works standalone, fails from
session 2, `docker exec getent` still resolves).

We have not reproduced dockerd's internal DNS failure here, and the
precise dockerd behaviour is theirs, not ours — but the churn is ours
and is avoidable.

**Immediate workaround — tell them today.** `reuse=True` keeps
`keptContainers` non-empty, so the network is never torn down between
tests. That should sidestep the whole problem at far lower cost than
the DNS-free topology they built.

**Fix.** Hoist network creation to run scope. Create once per
`faultbox test` invocation, remove in `cleanup()`, which already
handles it ([`runtime.go:1199`](../../internal/star/runtime.go)).
Per-test isolation is provided by container lifecycle, not by network
lifecycle; nothing depends on the network being recreated.

**Tests.** A multi-test container suite asserting the network ID is
stable across tests and that name resolution works in every test.

**Risk.** Low. Narrows resource churn. Watch for leaked networks on
abnormal exit — the existing sweep in
[`docker.go:294`](../../internal/container/docker.go) covers it.

**Also record** the grpc-go `dns:///` TXT-lookup aggravator they
document, as a troubleshooting entry. That one is not our bug, but it
cost them a 3 s deadline and the diagnosis is worth writing down.

## F-5 — Startup failure misdiagnosed as `TIMEOUT_DURING_FAULT`

**Root cause — confirmed.** [`internal/star/results.go:465`](../../internal/star/results.go)
gates only on `failed && tto.FailureType == "timeout"`. Nothing checks
that a fault exists. With zero faults, `faultedSvc` stays empty and the
generic suggestion is used — but the code is still
`TIMEOUT_DURING_FAULT` and the message still reads *"test timed out
while faults were active"*, which is false.

**Fix.**

- (b) Gate the classifier on `len(tto.Faults) > 0`. Emit a distinct
  `TIMEOUT_DURING_STARTUP` when the run has no faults and the failure is
  service startup, pointing at the service that never became ready.
- (a) Fail fast on a missing local image. When a tag looks local
  (no registry host, or `:local`-style) and is absent from the daemon,
  say *"image not found locally — did you forget to build it?"* instead
  of burning two minutes on a pull that ends in `denied:`.

**Tests.** Golden diagnostics for a fault-free timeout; unit for the
local-image classifier.

**Risk.** Minimal.

**Why this matters more than its severity suggests.** A classifier that
confidently names a cause that does not exist teaches people to
distrust every other diagnostic. This is cheap to fix and protects the
credibility of the whole diagnostics surface.

## F-6 — `replay` breaks on specs in a subdirectory, and prints a hint that cannot work

**Root cause — confirmed, two parts:**

1. **Path.** The extractor strips the `spec/` prefix and writes to
   `<dst>/<rel>` ([`cmd/faultbox/replay.go:186`](../../cmd/faultbox/replay.go)),
   so bundle entry `spec/spec.star` lands at `<dst>/spec.star`. But the
   root is computed as
   `rootInExtract := filepath.Join(dst, man.SpecRoot)`
   ([`replay.go:130`](../../cmd/faultbox/replay.go)) using the
   *original* relative path — `<dst>/faultbox/spec.star`. Mismatch →
   ENOENT. A spec at the repo root works (`SpecRoot == "faultbox.star"`),
   which is why every internal spec has always replayed fine and this
   never surfaced.

2. **Wrong hint.** [`cmd/faultbox/main.go:2402`](../../cmd/faultbox/main.go)
   prints `faultbox replay <bundle.fb> --test %s --seed %d`, but
   `replay`'s parser only accepts `--test=` and `--test <v>`
   ([`replay.go:46`](../../cmd/faultbox/replay.go)). There is no
   `--seed` case, and replay deliberately takes the seed from the
   manifest ([`replay.go:133`](../../cmd/faultbox/replay.go)) — so the
   flag is not merely unimplemented, it is meaningless. Every
   copy-pasted hint fails before it can hit the path bug.

**Fix.** Resolve the root against the extraction layout — store the
basename relative to the spec root's directory, or record both in the
manifest. Correct the printed hint to a command that runs. Add a
`--seed` that is accepted and ignored-with-a-note, or drop it from the
hint entirely; dropping is cleaner.

**Tests.** Round-trip a bundle whose spec lives in a subdirectory and
replay it. Assert the printed hint is executable — a string-equality
gate between the hint and `replay`'s accepted flags, so the two cannot
drift again.

**Risk.** Minimal. Bundle format unchanged if we derive the path at
read time; if we add a manifest field, it is additive and does not bump
`schema_version` (per the rules in `docs/bundles.md`).

## F-7 — Packet faults never reached a containerized consumer

Added to the report after the plan was written. Reported as the netstack
gateway attaching "on some runs and not others, same spec, same seed",
plus a second half: that the workarounds for F-3 and F-4 make packet
faults unreachable, with no configuration that both runs a multi-test
suite and injects packet faults.

**Root cause — confirmed.**

The gateway address for a container consumer is allocated inside a branch
gated on `faultedInterfaces()` — "does a **proxy** fault target this
interface". Packet faults are invisible to that question:
`faultedInterfaces` reads `fault_assumption` proxy rules, and packet
faults cannot be declared there at all — `FaultAssumptionDef` has no
packet-rule field. `partition()` and `packet_*` are body-time calls
recorded in a separate registry.

So a spec whose only faults were packet faults got no gateway address for
a container consumer, and the gateway never attached.

**Fixed.** The gate does not apply when the packet gateway is enabled: a
spec declaring `determinism(runtime = "gvisor")` has asked to be mediated
at the packet layer. `gatewayAddrFor` still returns `""` when the gateway
cannot attach, so the proxy fallback is unchanged.

**Their second half is resolved by F-1 and F-3, not by this.** Host ports
were a workaround for the proxy freeze (F-1, actually the supervisor
dying), and container names failing from test 2 was the network being
destroyed and never recreated (F-3). With both fixed, the
container-network path packet faults require is available again. Their
measured evidence fits: *"test 1 passed, all seven later tests failed"* is
the F-3 signature. **Confirm with them rather than asserting it.**

**Their suggestion to fail at setup is not implementable as stated**, and
the attempt is recorded rather than dropped. Packet faults are body-time
calls, so their arguments are validated inside the body; failing at setup
pre-empts that and replaces a spec error the author can fix (`source=`
naming the interface owner) with an environment error they cannot (no
`CAP_NET_ADMIN`). Three existing validation tests failed exactly that way,
on both platforms.

What was missing was the *reason*. The gateway is now attached at setup
purely to capture why it failed, and the post-hoc failure carries it.

**Remaining.** The reported *nondeterminism* is not explained. The gate
bug is deterministic — it would fail every run, not some. Either their
spec mixes proxy and packet faults so the gate opened for some
interfaces, or there is a second cause in TUN device lifecycle
(`fbox<pid>` naming, the orphan sweep). **Needs their bundle**, and it is
the open question that should gate calling F-7 closed.

## Release gate

Beyond the standard checklist:

- The F-1 regression test must run in CI, not only in Lima. If it can
  only run under real seccomp, it belongs in the Lima sweep and the
  sweep must be part of the release gate — a regression corpus that
  nobody runs is how this shipped.
- Re-run the reporter's topology shape before tagging: containerized
  SUT + `mock_service` + multi-test suite + proxied MySQL. Every one of
  the six issues touches that shape, and none of our corpus specs cover
  it. Ask them to re-run their suite against a pre-release build.

## Open questions

- **F-1:** does the fix hold under their real workload? Ours is a
  synthetic pool. Worth asking for a `.fb` bundle from a failing run to
  confirm the signature matches before we call it closed.
- **F-3:** confirm `reuse=True` actually sidesteps it on Docker 29.3.1
  before we recommend it as the interim answer.
- **F-2:** binding mocks to `0.0.0.0` on a developer laptop is a real
  exposure change. Same trade as proxies, but it should be a conscious
  call, not a side effect.

## Not in scope

A latent defect found while investigating, unrelated to the report and
deserving its own issue: `requiredSyscallsForService`
([`runtime.go:4115`](../../internal/star/runtime.go)) decides filter
installation by **grepping the spec source text** for
`fault(<var>,` on a single line. A `fault()` call formatted across
multiple lines — normal in a real spec — matches nothing, so no filter
is installed and the fault silently never fires. Same failure class as
the v0.13.3 silent no-ops. Needs its own investigation and fix.
