# Proposal: four changes to make v0.14.0 cover peer-mesh topologies

**Date:** 2026-07-28
**Status:** Proposal — amendment to [RFC-054](https://github.com/faultbox/Faultbox/issues/144), scoped to v0.14.0
**Branch:** `epic/v0.14.0-gvisor` (M0–M5 landed)
**Motivating workload:** [`poc/raft-cluster/`](../../poc/raft-cluster/) — 3-node `hashicorp/raft`, chain-of-blocks FSM
**Background:** [Raft gap analysis](2026-07-28-raft-antithesis-gap-analysis.md)

---

## Summary

RFC-054's packet gateway is the right mechanism for the fault class the
[Antithesis Raft study](https://antithesis.com/blog/2026/finding-bugs-in-raft-implementations/)
exercises, and M0–M5 have already landed it. Applied to a three-node Raft
cluster, though, it currently injects nothing — the SUT never receives a gateway
address, because address allocation is gated on a *proxy* address that does not
exist yet for a cyclic topology.

The fix is small and localized. **Four changes**, listed in dependency order.
Only the first is blocking; the rest turn a working mechanism into a usable one.

| # | Change | Size | Blocking? |
|---|--------|------|-----------|
| 1 | Gateway falls back to the real upstream when no proxy is running | ~10 lines | **Yes** — nothing works for a mesh without it |
| 2 | Wire `source=` into rule installation | ~40 lines | No — but no asymmetric partitions without it |
| 3 | Rebuild `partition()` on the packet gateway | ~80 lines | No — `packet_drop` covers it verbatim |
| 4 | Give `EventVal` the `.data` auto-decode that `StarlarkEvent` has | ~15 lines | No — but every cross-node monitor hits it |

Acceptance criterion for all four: **`poc/raft-cluster/faultbox.star` passes**,
including `test_isolate_leader_from_quorum`, which asserts that a leader cut off
from its entire quorum commits nothing. That test fails today by design.

## Why this workload is worth the amendment

A peer mesh is not an exotic shape. Raft, etcd, Cassandra, CockroachDB, NATS
clustering, Elasticsearch, and every gossip protocol are meshes. RFC-054's
Milestone 0 spike evaluated insertion candidates on "does traffic arrive, added
latency, container restart, Lima, CI" — all client→server questions. **No
criterion covered a cyclic topology**, so candidate A was selected without the
mesh case being tested, and it inherited an ordering assumption that only holds
for a dependency tree.

That is not an argument for revisiting the M0 decision. Candidate A is fine; the
gate in front of it is wrong.

## Change 1 — the gateway must not depend on a proxy existing

**Blocking. Nothing else in this proposal matters until it lands.**

### The defect

[`packetgateway_wire.go`](../../internal/star/packetgateway_wire.go), `gatewayAddrFor`:

```go
func (rt *Runtime) gatewayAddrFor(consumer, service, iface string, port int, upstream string) string {
    if !rt.packetGatewayEnabled() || upstream == "" {
        return ""
    }
```

and its caller in `buildEnv`:

```go
mediated := rt.proxyMgr.GetProxyAddr(name, ifName)
if gwAddr := rt.gatewayAddrFor(svc.Name, name, ifName, iface.Port, mediated); gwAddr != "" {
    mediated = gwAddr
}
```

`upstream` is the **proxy** address. `preStartProxies` starts an interface's
proxy when its owning service starts, and only services launched afterwards see
it. A mesh is a cycle, so for at least one link the proxy is always absent when
the consumer's env is built — `mediated` is `""`, the guard trips, and the SUT
gets the real address. Packet rules then install into a link no traffic crosses.

Measured on the Raft POC before the gVisor runtime existed, with the same
underlying cause:

```
{"event":"node.started","node":"node1","bind":"127.0.0.1:8301","advertise":"localhost:8301"}
```

Every node advertised its real port. To get *any* mediation, the POC has to
order services `node3 → node2 → node1` and elect node1 sole bootstrapper — and
even that leaves node1's own inbound link unmediated. No ordering covers a cycle.

To the branch's credit, this fails loudly rather than quietly:
`unwiredInstalls()` fails the test rather than letting a packet fault that
touched nothing report a pass. That is the right call and should stay. But the
test fails; it does not work.

### The fix

The guard conflates "no proxy" with "no upstream". The real upstream is known at
spec load and already has a helper — `proxyTargetAddr(svc, iface)`, which is
RFC-036-aware and handles `HostPort`:

```go
mediated := rt.proxyMgr.GetProxyAddr(name, ifName)
upstream := mediated
if upstream == "" {
    // No proxy for this interface yet — in a cyclic topology there may
    // never be one before this consumer's env is built. The gateway can
    // still relay straight to the real upstream, which is known at spec
    // load. Chaining through a proxy is an optimization, not a precondition.
    upstream = proxyTargetAddr(s, iface)
}
if gwAddr := rt.gatewayAddrFor(svc.Name, name, ifName, iface.Port, upstream); gwAddr != "" {
    mediated = gwAddr
}
```

The same treatment applies to `proxyAddrSubstitutionsConsumer`, which has the
identical `continue`-on-empty shape.

The `upstream == ""` guard inside `gatewayAddrFor` should then become a hard
error rather than a silent `""` return — with both call sites supplying a
fallback, an empty upstream is a bug, not a state to tolerate.

### Ordering caveat, stated honestly

This makes the gateway address available at env-build time for every service
regardless of start order. It does **not** make the proxy available — a mesh
link whose peer started later still bypasses the L7 proxy and relays
gateway→upstream directly. Packet faults work on every link; protocol-level
faults (`error()`, `response()`) still do not, for the late links.

Fully closing that needs proxies pre-started for all interfaces before any
service launches. That is independently feasible — the tcp proxy dials its
upstream lazily per connection, so a listener can exist before its upstream does
— but it is a separate change with its own blast radius, and packet faults are
what this workload needs. **Recommend deferring to v0.14.1** and documenting the
limit.

## Change 2 — wire `source=` into rule installation

### Status

The mechanism is already built. From [`netfault/alloc.go`](../../internal/netfault/alloc.go):

> One address per triple — rather than one shared address with per-flow
> bookkeeping — is what makes `fault(db.main, source=worker)` work without the
> packet's source IP. Docker masquerades container traffic, so the source IP
> arrives as the bridge gateway and cannot identify the sender; the destination
> can, because we chose it. See RFC-054 decision record M0.2.

Every `(consumer, service, interface)` triple gets a distinct gateway address.
That is exactly the right design, and it is exactly what per-peer targeting needs.

But `source=` is still parsed, stored, emitted into the trace, and then dropped
on the floor — [`builtins.go:2517-2588`](../../internal/star/builtins.go#L2517-L2588),
unchanged from main. `PacketGateway.InstallRules(service, iface, rules)` has no
consumer parameter, so a rule on `node2.raft` fires for traffic from every peer.

### Why a mesh needs it

In a client→server topology, "fault this interface" is usually what you mean. In
a mesh it almost never is. The Raft faults that matter are pairwise and often
asymmetric:

- Isolate node1 from node2, leaving node3 reachable → minority/majority split
- Drop only node1→node2, leaving node2→node1 intact → the classic one-way
  partition where a leader keeps its lease while its followers time out

Neither is expressible without per-source rules. `where=lambda p: p.dst_ip ==
...` is not a real workaround: it hardcodes an allocated address into the spec,
costs a Starlark call per packet, and the RFC itself warns that an impure lambda
silently breaks replay.

### The change

Thread the consumer through installation:

```go
InstallRules(consumer, service, iface string, rules []*netfault.Rule) error
```

`consumer == ""` keeps today's meaning (all sources). When set, the gateway
applies the rules only to the `GatewayAddr` whose triple matches — no packet
inspection, no per-flow bookkeeping, just rule scoping by the address the
allocator already assigned. The registry key becomes the triple instead of the
pair.

Then `builtinFaultProtocol` passes `sourceSvc` instead of only reporting it. A
`source=` naming a service that does not consume the interface should error at
spec load — silently matching nothing is how the current bug hides.

**This also fixes `source=` for the 14 L7 proxies**, where it is documented
(`spec-language.md:1881-1889`) and equally non-functional. Worth doing in the
same change so there is one story rather than two.

## Change 3 — rebuild `partition()` on the packet gateway

`partition()` on the epic branch is byte-identical to main: a `connect` deny
filtered by destination, hardcoded to `127.0.0.1:<port>`. Against a mesh it is a
guaranteed no-op — the trace shows `partition_applied` firing with **zero**
`connect` syscalls intercepted, because peers pool connections and stop calling
`connect` once the cluster forms.

With changes 1 and 2, `partition()` becomes a thin composition:

```python
partition(node1, node2, run=scenario)                    # bidirectional blackhole
partition(node1, node2, direction="a_to_b", run=scenario) # one-way
partition_start(node1, node2); ...; partition_stop(node1, node2)
```

desugaring to `packet_drop` on the relevant `(consumer, service, interface)`
triples in the requested directions. `ActionDrop` already has the right
semantics — the comment in `netfault/rule.go` states it precisely:

> No RST is sent — the packet simply never existed. This is what makes the
> half-open blackhole scenario possible; closing a connection would send a RST
> that clients handle correctly.

That is what a partition is, and what `connect`-deny never was.

Under `runtime="default"`, `partition()` should **error at spec load** with a
pointer to `runtime="gvisor"`, not fall back to `connect` deny. A primitive that
silently does nothing against any connection-pooling service is worse than one
that refuses.

Add `partition_start`/`partition_stop` while here — the `run=` callback form
alone makes it awkward to hold a partition across a multi-step scenario, which
is precisely how the leadership-transfer bug is reached.

## Change 4 — `EventVal.data` auto-decode

Small, unrelated to gVisor, and hit immediately by anyone writing the cross-node
monitor this workload needs.

`spec-language.md:1162-1165` documents this monitor:

```python
monitor("no_stdout_errors",
    on    = match.event(type="stdout"),
    check = lambda event, state: "ERROR" not in event.data.get("level", ""),
)
```

It cannot work. Monitors receive an `EventVal`
([`trace.go:241`](../../internal/star/trace.go#L241)), which has no `.data`
attribute and falls through to a raw string field lookup. The documented example
fails with `string has no .get field or method` — reproduced while writing the
Raft monitor. Only `StarlarkEvent`, used by `where=` predicates, auto-decodes
`.data` into a dict.

Give `EventVal` the same auto-decode `StarlarkEvent` has
([`types.go:703-740`](../../internal/star/types.go#L703-L740)). Flat field
access (`event.count`) already works and should keep working; this only adds the
documented form. The alternative — fixing the docs to match the code — is
cheaper but leaves two event types with gratuitously different surfaces.

## Acceptance

`poc/raft-cluster/` is the test. It exists, it runs, and its assertions already
encode the target behaviour.

**After change 1** — packet faults reach peer links. `packet_drop` on both
followers' raft interfaces makes the leader lose quorum:
`test_isolate_leader_from_quorum` goes from failing (`88 != 0`) to passing.

**After change 2** — asymmetric partitions become expressible:

```python
fault(node2.raft, source=node1, packet_drop(dir="c2s"), run=scenario)
```

**After change 3** — the same scenario reads as intent rather than mechanism:

```python
partition_start(node1, node2, direction="a_to_b")
```

**After change 4** — the state-machine-safety monitor can be written the way the
docs describe.

Two further scenarios become reachable and are worth landing as specs, because
each targets a bug Antithesis actually found in `hashicorp/raft`:

```python
def test_transfer_during_partition():
    """Leadership transfer while the leader loses quorum.
    Antithesis bug 2: the transfer goroutine blocks forever and the global
    'transfer in progress' flag never clears, so the node cannot serve
    clients even after it is re-elected."""
    partition_start(node1, node2)
    node1.admin.post(path="/transfer")
    partition_stop(node1, node2)
    assert_true(wait_leader(), "cluster never recovered a leader")
    assert_true(submit(5) > 0, "cluster accepted no commands after transfer")

def test_snapshot_install_livelock():
    """Isolate a follower long enough that it needs InstallSnapshot.
    Antithesis bug 3: the follower retains stale log entries after
    installing a snapshot, fails the next AppendEntries prevLogIndex
    check, and the leader re-sends a snapshot forever."""
    def scenario():
        submit(200)                      # outrun SnapshotThreshold=16
        node1.admin.post(path="/snapshot")
    partition(node1, node3, run=scenario)
    assert_true(converged(), "node3 never caught up after rejoining")
```

Both are more demanding acceptance tests for the packet gateway than a Postgres
container, and Milestone 4's exit criterion — "all twelve scenarios as
executable specs" — would be considerably better served by scenario 1 (silent
blackhole) demonstrated against a cluster that genuinely loses quorum.

## Explicitly out of scope for v0.14.0

**Antithesis bug 1 — the async heartbeat race.** A goroutine race between
`hashicorp/raft`'s transport thread and its main loop. Packet timing influences
the window; it does not control it. RFC-054 correctly caps at L1 and does not
claim otherwise. Reaching it needs [RFC-053](https://github.com/faultbox/Faultbox/issues/143)
Path D (`interleavings="sut-internal"`), for the reason RFC-053 states plainly:
seccomp reports M, not G, so no amount of syscall or packet mediation attributes
an event to a goroutine.

Worth noting for sequencing: RFC-053 Phase 0 flags that `--explore=all` sizes its
exploration space from a `time.Sleep(50 * time.Millisecond)` accumulation window,
so on a loaded runner it explores less and still reports exhaustion. Any plan to
find bug 1 by randomized search across seeds depends on that being fixed first.

**Pre-starting all proxies.** See the caveat under change 1. Defer to v0.14.1.

**`bandwidth()` / `mtu()`.** Already deferred to v0.14.1 on the branch. Neither
is needed here.

## Estimate

Changes 1 and 4 are each under an hour plus tests. Change 2 is the real work —
an interface change through the gateway, the registry, and both fault paths,
call it a day with tests. Change 3 is a day including the spec-load error path
and `partition_start`/`partition_stop`.

Roughly **three days**, against a release whose mechanism is already built and
whose headline scenario is currently unreachable for an entire class of
topology.
